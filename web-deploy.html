NoteTaker · Phase 4 proposal · deployment

Ship it to the web.

A plan to publish NoteTaker as a hosted web app alongside the desktop build — what it costs, what it wins, what breaks, and the exact steps to get there. The headline: the frontend already runs in a browser today, so this is a hosting-and-trade-offs decision, not a rewrite.

01

The choice

Publish the existing React/TypeScript frontend as a static single-page web app served from a URL, so anyone can open NoteTaker in a browser tab with no install. The desktop (Tauri) app does not go away — web becomes a second distribution of the same codebase, pointed at the same Firebase backend. A user who signs in gets the same map library whether they opened the installer or the link.

Web is the front door (try instantly, sync everywhere); desktop stays the power tool (overlay, global hotkey, durable files, video download).

This is feasible at low cost because of how the app was built. NoteTaker is a Vite + React app wrapped in a thin Rust shell. Every Tauri-only capability already sits behind a src/platform/* module that branches on a single runtime flag — isTauri = "__TAURI_INTERNALS__" in window (src/platform/window.ts) — and each one already has a browser fallback written. Running npm run dev / npm run build today produces a working browser app; that path has existed since Phase 1.

02

Why it's cheap: the web build exists

The scope of "deploy as a web app" is unusually small because we are not building a web app — we are hosting one that already compiles. The work is (a) decide what to do about the handful of features that degrade or vanish without a native shell, (b) move a few pieces of config from Tauri to the web host, and (c) put the dist/ folder on a static host.

The single most important consequence is the loss of the always-on-top frameless overlay — the app's defining form factor. The subtlest cost is keyboard: NoteTaker is keyboard-first, and several of its shortcuts collide with the browser's own — one, Ctrl+T, can't be reclaimed by a web page at all (§04). Everything else is a graceful degradation or an outright win. The rest of this document is the careful accounting of those four columns and the steps that follow from them.

03

Effect on the app: two products, one code

Shipping web reframes NoteTaker from "a desktop overlay" into "a note app with a desktop overlay and a web edition." The two editions diverge on form factor and storage, and converge on everything else through the shared Firebase account.

Desktop · Tauri

The overlay companion

  • Floats over any app — always-on-top, frameless, snaps to a screen edge.
  • Global hotkey Ctrl+Alt+N shows/hides it from anywhere.
  • Durable local files — one JSON per map under the app data dir.
  • Video download — yt-dlp + ffmpeg rescue embed-blocked videos.
  • Distributed as a signed installer per OS.
Web · static SPA

The zero-install edition

  • Opens in a tab — used side-by-side via OS window snapping or Picture-in-Picture.
  • In-app shortcuts only while the tab is focused; no OS-global hotkey.
  • Sync-first storage — localStorage/IndexedDB locally, Firestore when signed in.
  • Embed-blocked videos fall back to the session timer (no download path).
  • Distributed as a URL — instant try, shareable, always current.

Because both editions read the same MapStore interface and the same Firestore tree (users/<uid>/maps/<id>), a signed-in user's notes are continuous across the two: start on the desktop overlay during a lecture, review on the web from a different machine. That continuity is the strategic payoff of shipping web on the existing backend rather than as a separate thing.

Cross-cutting · desktop + web

Both editions need a notes-only mode — make the video player hideable.

Today the embedded player only disappears on its own for external sources (PlayerPanel.tsx:44 returns null — the live-lecture / Zoom case), and the focus layout shrinks it to a floating mini-player rather than removing it (platform/layout.ts). Neither is an explicit, user-controlled "hide the player." Both editions want one. On desktop, a live in-person or Zoom lecture needs notes at full height with no video pane at all. On web, the common setup is a split screen with the video playing on its own site in the other half — so the in-app player is pure redundancy. The change is small and shared: a persisted player-visibility toggle (a new "notes-only" layout, or a flag in uiPrefs like playerHeight) that hands notes 100% of the canvas, decoupled from source type. On web it should be the default layout — and it cleanly defuses the lost video-download and video-persistence concerns below, since a split-screen user never leans on the in-app player.

Cross-cutting · desktop + web

Give the live-lecture timer a real pause — and split pause from reset.

In a live lecture there's no video, so notes are stamped against the session timer — a pure wall-clock count (ExternalController.getCurrentTime() = (Date.now() − start) / 1000, PlayerController.ts:32). It has no pause concept, and the only control is the timer chip in the title bar, where a single click resets it (TopBar.tsx → resetSession re-anchors sessionStart to now, store.ts:534). Two problems: a break, tangent, or stepping away keeps the clock running, so later stamps drift from real lecture time; and one ambiguous click silently wipes the elapsed count. Change (both editions): a clear Pause / Resume toggle plus a distinct Reset button. This needs a genuine pause model — accumulate elapsed seconds and track a "running-since" epoch instead of a single start, and persist it on the map (extend the current sessionStart) so a pause survives reload and sync. Ctrl+Space — today a no-op for external sources — can then pause/resume the timer in live-lecture mode. All of this lives in the shared store / controller layer, so desktop and web get it together.

04

Effect on the features

Every shipped feature, sorted by what the browser does to it. Locations point at the code that already decides the behaviour.

Works as-is  no change in the browser

Outline capture & structure

keep
src/components/Outline/* · src/state/store.ts

Pure React + Zustand. Typing, Enter for a sibling, ⌫, arrow-key navigation, reorder, collapse and undo/redo all work in a tab. The modifier shortcuts and Tab-to-indent are a separate story — they collide with the browser and are pulled out as a degrade below.

Map view, cross-links, fullscreen

keep
src/components/Map/MapView.tsx (React Flow + dagre, React.lazy)

Renders and lays out identically; the lazy chunk just downloads over HTTP instead of from disk. Drag-to-link and the in-canvas fullscreen toggle are DOM-only.

YouTube embed + click-to-seek

keep
src/components/Player/YouTubePlayer.tsx · src/player/youtubeApi.ts

It's an <iframe> driving the YouTube IFrame API — a web technology to begin with. Seeking from a timestamped note works unchanged (host CSP must allow frame-src youtube.com; see §06).

Transcript import + live drawer

keep
src/transcript/import.ts (transient <input type=file> + File.text())

Deliberately built to never need a filesystem path — it reads the file's text in-memory. Identical in browser and desktop. Cues persist inside the map.

Command / jump palettes, maps switcher, help, onboarding, themes

keep
src/components/Palette/* · Help/* · Onboarding/* · platform/theme.ts

All presentation + state. Light/dark/system theming is CSS variables; the help overlay and onboarding are plain React. No native dependency anywhere.

Markdown / Obsidian export

keep
src/platform/exportFile.ts:22 (Blob download fallback)

The browser branch triggers a normal file download via a Blob URL. Functionally complete — the only difference from desktop is no native "Save As" dialog.

Improves  the web is the better host

Google sign-in

simpler
src/auth/authStore.ts:180 — signInWithPopup

The browser uses Firebase's first-class signInWithPopup. The whole desktop apparatus — a Rust system-browser loopback OAuth + PKCE flow (src/auth/desktopSignIn.ts, the desktop_google_sign_in Rust command, an embedded client secret) — is not needed on web. Web sign-in is the easy path the desktop has to emulate.

Cloud sync becomes the safe default

safer
src/storage/sync.ts (local-first mirror to Firestore)

On desktop, local files are durable, so sync is a bonus. On web, browser storage is evictable — so being signed in is the recommended mode, and the existing sync engine already provides it. The feature gains importance rather than function.

Distribution & onboarding

new
n/a — a property of being a URL

No download, no OS gatekeeper, no per-platform installer. A link that's always the latest version, shareable, and try-before-you-install. This is the main growth argument for shipping web at all.

Degrades  usable, with caveats

Keyboard shortcuts & Tab-to-indent

collides
src/keyboard/keymap.ts · useKeyboard.ts — 20+ bindings, most Ctrl-based

The app is keyboard-first and the browser owns many of the same keys. Three tiers:
· Interceptable — most combos (Ctrl+S save-page, Ctrl+P print, Ctrl+O open, Ctrl+K omnibox) and Tab/⇧Tab focus-traversal can be reclaimed with preventDefault() while focus is in the app — which it already does in dev. Brittle (focus-dependent) but workable.
· Reserved, NOT interceptable — a web page cannot stop Ctrl+T (new tab), Ctrl+N (new window), or Ctrl+W (close tab). NoteTaker's Ctrl+T = insert / refresh timestamp is a primary capture action and a direct casualty: on web it would open a browser tab.
· Editing conflicts — Ctrl+←/→ (rewind / forward video) clashes with word-by-word cursor motion inside a note's text.
Fix: a web-specific keymap that rebinds the reserved combos (above all Ctrl+T), plus the §08 PWA — an installed / fullscreen app can use the Keyboard Lock API (navigator.keyboard.lock()) to capture even Ctrl+T / Ctrl+W. Trapping Tab also needs an accessibility escape so keyboard users aren't stuck in the outline.

Local video persistence

re-pick
src/platform/dialog.ts:52 — object-URL fallback

The video still plays: the browser opens it via URL.createObjectURL. But a web page can't know a file's real path, so it cannot be reloaded across sessions — the user re-picks the file each time. Desktop keeps the real filePath and reloads through asset://. (Click-to-seek within a session is unaffected; and for the split-screen / notes-only web user in §03 this rarely matters — they play the file in their own player.)

Save / open dialogs

browser-native
exportFile.ts · dialog.ts · transcript/import.ts

Native OS dialogs become browser download + <input type=file>. No lost capability, just a less "native" feel and no chosen-path memory.

Flush-on-exit guarantee

best-effort
src/platform/lifecycle.ts · fileStore.ts:210 (saveSync)

Desktop holds the window close, awaits an async flush, then destroys it. Web relies on visibilitychange/beforeunload + a synchronous localStorage write (already implemented as saveSync). Solid in practice, but the browser gives weaker guarantees than the native close handler.

Lost  requires the native shell

Always-on-top overlay (frameless, snap-to-edge)

gone
src-tauri/src/lib.rs · platform/window.ts (all no-op in browser)

The defining form factor. A web page cannot float above other applications, remove its own chrome, or snap to a screen edge. On web you place the tab beside the lecture via OS window-snapping, or pop the video out with Picture-in-Picture. The min / maximize / close buttons in the title bar (TopBar.tsx:89) become dead controls and must be hidden on web.

Global show/hide hotkey

gone
Ctrl+Alt+N — registered in Rust (tauri-plugin-global-shortcut)

OS-level global shortcuts need a native process. In-app shortcuts still work while the tab is focused; there's just no way to summon the tab from another app.

High-quality YouTube download (yt-dlp + ffmpeg)

gone
src/platform/youtubeDownload.ts (returns null/false without a shell)

Needs a native process to run a binary and write a cache. So an embed-blocked video on web degrades to the session timer (no seek) instead of the download-and-play rescue. Note this cannot be a pure client-side web feature regardless: a browser can't fetch YouTube's video bytes cross-origin (CORS). Returning it to web would require a server-side download service — explicitly out of scope (see §08). For the split-screen / notes-only web user (§03) it rarely bites — they're watching on YouTube directly.

05

Storage & durability — the real risk

This deserves its own section because it's the one place where the "free" web build has a sharp edge. The desktop writes durable JSON files. The browser's local-only mode writes localStorage (notetaker:maps:v2, src/storage/fileStore.ts), which is:

  • Small — a ~5 MB per-origin budget. And transcripts persist inside the map (NoteMap.transcript), so an imported .srt can consume a large fraction of that budget per map.
  • Rewritten whole on every save — writeAllWeb serializes the entire {id: NoteMap} object each time (fileStore.ts:67), so cost grows with the total library, not the edited map.
  • Evictable — the browser or the user can clear it; there's no file on disk to recover from.
Recommendation

Make signed-in the default on web, and upgrade local storage to IndexedDB.

Add an idbStore that implements the existing MapStore interface (list/load/save/remove) — far larger quota, per-map writes, no whole-library reserialization. It drops in behind the same activeStore = isTauri ? … : webStore switch with zero churn to callers. Pair it with nudging web users toward sign-in (Firestore) so their library has a durable home off-device. This is the one degradation worth actively engineering around.

06

Security & config deltas

A few responsibilities move from the Tauri shell to the web host. None are hard; all are easy to forget.

CSP moves to the host

Content-Security-Policy

The policy in tauri.conf.json is enforced by Tauri and does not apply to a web host. Serve an equivalent via response headers (or a <meta>), dropping the Tauri-only sources (asset:, ipc:, *.localhost).

Firebase auth domains

Authorize the prod origin

Popup sign-in only works from an Authorized domain. localhost is allowed by default; the deployed domain must be added in Firebase Console → Authentication → Settings.

Rules are the only guard

Deploy firestore.rules

On a public URL, the owner-only rules (already in firestore.rules) are the sole thing protecting data. firebase deploy --only firestore:rules is now a release gate, not optional.

No secret in the web bundle

Desktop secret stays desktop

The web build must build without VITE_GOOGLE_DESKTOP_CLIENT_SECRET — and it does: that var is read only in desktopSignIn.ts. Web needs just the four public VITE_FIREBASE_* keys (meant to ship to clients).

Native write surface gone

SEC-3 doesn't apply on web

There's no Rust save_text_file / asset-path command in the browser, so the desktop audit's arbitrary-file-write concern is structurally absent on the web target.

Base path

Subpath vs root

Root-domain or Netlify/Vercel/Firebase Hosting → default base:'/' is fine. A GitHub Pages project page serves under /NoteTakerUI/ and needs base set, or assets 404.

A production CSP, derived from the existing one minus the Tauri-only sources:

// served as a response header from the static host (or a <meta> tag)
default-src 'self';
script-src  'self' https://www.youtube.com https://s.ytimg.com;
style-src   'self' 'unsafe-inline' https://fonts.googleapis.com;
font-src    'self' https://fonts.gstatic.com data:;
img-src     'self' data: blob: https:;
media-src   'self' blob:;
connect-src 'self' https://identitytoolkit.googleapis.com https://securetoken.googleapis.com
            https://www.googleapis.com https://firestore.googleapis.com
            https://firebaseinstallations.googleapis.com;
frame-src   https://www.youtube.com https://www.youtube-nocookie.com;
object-src  'none'; base-uri 'self'

Note: the production Vite bundle loads external ES modules, so script-src 'self' holds without unsafe-inline/eval (those are only in Tauri's devCsp).

07

Changes necessary

Concrete edits, grouped by kind. The striking part: nothing here is a rewrite, and the build step already exists.

build

Confirm / set the base path & build output

~½ hr

npm run build already emits a deployable dist/ (Vite, with Firebase code-split per vite.config.ts). Only set base if hosting under a subpath. No new build pipeline.

code

Hide native-only UI when !isTauri

~2 hr

Gate the window min/maximize/close controls (TopBar.tsx:89) behind isTauri so they aren't dead buttons on web. Optionally add a one-time "web mode" notice explaining there's no overlay / global hotkey here. Small, surgical.

code

Web-specific keymap (reclaim the reserved combos)

~½ day

Rebind the browser-reserved shortcuts — above all Ctrl+T (timestamp) — to web-safe keys, and audit preventDefault() coverage for the interceptable ones. Pairs with the §08 PWA, which unlocks the Keyboard Lock API for the rest.

code

Notes-only mode / hideable player — both editions

~½ day

A persisted player-visibility toggle (new layout or uiPrefs flag) giving notes the full canvas, decoupled from source type. Serves the desktop live-lecture case and is the default layout on web (split-screen). Benefits desktop too, so it's shared, not web-only.

code

Session timer: pause / resume + a separate reset — both editions

~½ day

Give ExternalController a real pause model (accumulated elapsed + running-since, persisted on the map beyond sessionStart) and split the single reset-on-click chip into clear Pause/Resume and Reset controls; wire Ctrl+Space to pause/resume in live-lecture mode. Shared store/UI layer — not web-specific — but the live-lecture web user feels it most.

code

IndexedDB MapStore for web local mode

~1 day

New idbStore implementing the existing interface; swap it in for webStore behind the same runtime switch. Addresses the §05 durability risk. Optional for a first ship, recommended before promoting web.

host

Pick a static host + SPA rewrite

~1 hr

Recommended: Firebase Hosting — already in the stack, same project as Auth/Firestore, one firebase deploy, free TLS + custom domain, trivial SPA rewrite to index.html. Alternatives: Netlify / Vercel / Cloudflare Pages / GitHub Pages (mind the base-path caveat).

config

Backend + CSP wiring

~1 hr

Add the prod domain to Firebase Authorized domains; firebase deploy --only firestore:rules; serve the §06 CSP header; provide the four VITE_FIREBASE_* values to the web build (CI secrets).

ci

Web deploy workflow

~2 hr

A GitHub Actions job parallel to the existing release.yml: build the web bundle and deploy to the host on push to main (or a tag). Keeps the URL always-current with no manual step.

Desktop bug · fixed

The frameless window had a dead, non-draggable grey margin around the app — now it fills the window.

Symptom (was): the actual app (the cream card) was smaller than the window — a grey frame wrapped it, the window looked larger than it is, and that grey strip couldn't be dragged. Cause: .stage is the full-window backdrop (height:100vh; padding:18px + the dotted --desk-dot background) and .app filled it minus that 18px inset. The frameless window's bounds are the whole .stage, but only .bar-top carries data-tauri-drag-region — so the 18px frame was part of the window yet draggable nowhere and interactive nowhere. Fix shipped — fill the window: main.tsx now stamps data-platform="desktop" on the root element before first paint (gated on isTauri), and styles.css zeroes the inset and strips the card frame on that build — [data-platform="desktop"] .stage{padding:0; background-image:none} plus [data-platform="desktop"] .app{border:none; border-radius:0; box-shadow:none}. The window now equals the card: no grey strip, nothing that "looks bigger than it is." Scope: desktop-only — the browser build keeps its floating-card look untouched, since the margin there is merely cosmetic.

08

Implementation plan

Phased so there's a shippable, honest web app after Phase 1, with durability and app-likeness layered on after. Estimates are working days for one developer.

Phase 0 — Prove it · ~½ day · low risk

Smoke-test the existing web build

  • npm run build && npm run preview; open the bundle in a real browser.
  • Walk every feature: outline, map, YouTube seek, local video, transcript import, export, palettes, themes, undo, sign-in popup, sync.
  • Write down exactly what's dead (overlay, hotkey, download) and what's awkward (local-video re-pick). Confirms §04 against reality.
Exit gate: a verified list of works / degrades / dead in your browser.
Phase 1 — Make it honest & live · ~1–2 days

First real deployment to a staging URL

  • Gate native-only UI behind isTauri (window controls; optional web-mode notice).
  • Ship a web keymap (rebind Ctrl+T and the other reserved combos) and a notes-only default layout (hideable player) for the split-screen web case.
  • Add the session-timer pause/resume + reset controls (shared store change) so live-lecture stamps stay accurate through breaks.
  • Serve the §06 CSP; add the prod domain to Firebase Authorized domains; deploy firestore.rules.
  • Deploy dist/ to Firebase Hosting with an SPA rewrite; verify sign-in + a Firestore round-trip from the hosted origin.
Exit gate: a working URL where you can sign in and your maps load.
Phase 2 — Make it durable · ~2–3 days

Close the storage gap

  • Add the idbStore (IndexedDB) implementing MapStore; swap it in for web local mode.
  • Nudge web users toward sign-in; make signed-in the recommended default.
  • Verify sync round-trips browser ↔ desktop on one account — the cross-edition continuity promise.
Exit gate: a map edited on web appears on desktop (and vice-versa), and local web data survives a reload comfortably.
Phase 3 — Make it app-like · ~2–3 days · optional

Recover some of the native feel

  • PWA: web app manifest + service worker → installable, offline app shell, its own window.
  • Picture-in-Picture for the video (requestPictureInPicture) to partly recover a floating-player while notes stay in the tab.
  • Keyboard Lock API (navigator.keyboard.lock()) once installed / fullscreen — reclaims even the Ctrl+T / Ctrl+W a plain tab can't intercept, closing the §04 keyboard gap.
  • Responsive polish for narrow / tablet widths (the desktop assumes a wide window).
Exit gate: NoteTaker is installable from the browser and usable offline for already-loaded maps.
Phase 4 — Ship · ~½ day

Custom domain + automation + docs

  • Point a custom domain at the host; CI deploy on push to main/tag.
  • Update README with the live URL and a "web vs desktop" comparison; link it from the repo.
Exit gate: public URL, auto-deployed, documented.
Parked — out of scope

Server-side YouTube download

Returning the yt-dlp rescue to web is not a client change — a browser can't fetch YouTube bytes cross-origin. It would mean standing up a yt-dlp download service (a backend, a job queue, storage, and the same ToS exposure the desktop feature carries). That is a separate product decision; this plan deliberately leaves embed-blocked videos on the timer fallback for web.

09

Verdict

Do it. The web build already compiles; the cost is hosting plus a careful handling of three lost features, not an engineering project.

The leverage is high and the risk is low. Web becomes NoteTaker's front door — instant try, no install, sync-first, shareable — while the desktop app keeps the things only a native shell can do: the always-on-top overlay, the global hotkey, durable files, and the video download. One codebase, one Firebase backend, two complementary editions of the same notes.

Recommended first move: Phases 0–1 — prove the bundle in a browser, then put it on a Firebase Hosting URL behind the existing auth. That alone delivers a real, honest web app in two days. Layer IndexedDB durability (Phase 2) before promoting it widely, and treat the PWA polish (Phase 3) as the optional finish.
